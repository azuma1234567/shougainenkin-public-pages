# サイト構造の整理 — Codex 指示書 (2026-09-03)

`docs/site-structure-2026-09-03.md` の §2〜§4 を**この文書で置き換える**(あちらの §1 の測定値は有効)。

## 前提(運営者の判断、確定)
- このサイトに来るのは**障害年金を申請したい人**。制度を知らない人ではない。
- クリック上位3本のうち2本が申立書の記事。裁決91件の争点は 程度57 / 初診日35 / 診断書15 / 納付10。**落ちる場所は書類の中身**。年金事務所の場所で落ちた人はいない。
- 5つの機能は同じ種類のものではない。**申請の行程のどこで使うかが違う**。だから1列に並べず、行程の中に置く。

| 機能 | 使う段階 | 手元に要るもの |
|---|---|---|
| 申立書を、自分で書きたい | 書類を作っている(いちばん重い) | 発病から今までの記憶 |
| 私は何級くらい？ | 診断書を受け取った直後 | 診断書の裏面 |
| 何をそろえればいい？ | 申請すると決めた | なし |
| いくらもらえる？ | 申請前の生活設計 | なし |
| どこに出せばいい？ | 最後の1分 | 住所 |

## §1 トップページ(app/page.tsx)

並びをこうする。**「自分の場合を、確かめる」の帯は消す**(5機能は §1-2 の各ステップに入る)。「自分でやるか、頼むか」の独立セクションも消す(§1-4 の探す軸に入る)。

```
1 hero(いまのまま)
2 申請の流れ ― 8つのステップ   ← hero の直下へ移動。各ステップに機能を埋め込む
3 障害年金、はじめてですか？     (いまのまま3枚)
4 探す                          (5軸。見出しを「どこから探しますか」→「探す」に)
5 その心配、誤解かもしれません   (いまのまま。/gokai へのリンクは対応済み)
6 一度「不支給」でも…            (いまのまま)
```

### 1-2 「申請の流れ」に機能を埋め込む
8ステップの並びは変えない。該当ステップの下に、その段階で使う機能のカード(既存の `DouguCard`)を1枚置く。

| ステップ | 埋め込む機能 | カードの1行 |
|---|---|---|
| 3 年金事務所へ相談する | どこに出せばいい？ | 管轄の年金事務所と、予約のしかた |
| 4 必要書類をそろえる | 何をそろえればいい？ | 自分の場合に要る書類だけを一覧に |
| 5 診断書の準備をする | 私は何級くらい？ | **受け取った診断書の裏面を、国の目安表に当てはめる** |
| 6 申立書を作成する | 申立書を、自分で書きたい | 期間ごとに書いて、公式様式に重ねて印刷 |

- 6 のカードだけ**他より大きく**する(`p-card-lg`)。いちばん重い書類で、来ている人の半分がここで困っている。
- 「いくらもらえる？」はステップに入れない(結果を変えないため)。`/hajimete` と `/okane/ikura` に置いてあるので、そこに任せる。
- セクションの見出しは「はじめての方は、8つのステップで」→**「申請の流れ ― 8つのステップ」**に。lead は「初診日の確認から結果が届くまで。**それぞれの段階で使える機能を、そのステップに置いています。**」
- `href="/shinsei" linkLabel="申請の流れを詳しく見る"` はそのまま。

## §4 「5機能」というまとまりを解体する
運営者の判断: 5つを1つのカテゴリとして扱うのをやめる。それぞれを本来の親の下に置く。

| 機能 | 親 | パンくず(2段目) |
|---|---|---|
| 申立書を、自分で書きたい | 申請の流れ(ステップ6) | 申請の流れ |
| 私は何級くらい？ | 申請の流れ(ステップ5) | 申請の流れ |
| 何をそろえればいい？ | 申請の流れ(ステップ4) | 申請の流れ |
| どこに出せばいい？ | 申請の流れ(ステップ3) | 申請の流れ |
| いくらもらえる？ | お金の話 | お金の話 |

### 4-1 `/dougu` の一覧ページを廃止し、`/shinsei` へ 301
- `app/dougu/page.tsx` を消し、`next.config` の redirects に `/dougu → /shinsei`(permanent)を足す。機能の一覧は「申請の流れ」そのものになる。
- `app/sitemap.ts` から `/dougu` を外す(`/dougu/*` の5本は残す)。
- `lib/published-links.ts`: `/dougu` 自体はリンク先にしない。5本はこれまでどおり公開。
- prelaunch-check の C-5(リダイレクト)の対象に `/dougu` を足し、301 で `/shinsei` に着くことを検査する。
- **URL `/dougu/*` は変えない**(公開済み・sitemap 収録済み・5つの検証記録が参照)。

### 4-2 各機能ページのパンくずと「戻る」
- `Breadcrumb` の2段目を上の表の親にする。`/dougu/kingaku` だけ「お金の話」(`/okane`)、他の4つは「申請の流れ」(`/shinsei`)。
- 各機能ページの末尾にある「一覧へ戻る」相当のリンクは、親へ戻す(申請の流れ / お金の話)。
- 各機能ページの「ここからできること」の相互リンクは、行程の前後だけに絞る:
  - どこに出せばいい？ → 何をそろえればいい？
  - 何をそろえればいい？ → 私は何級くらい？ / 申立書を、自分で書きたい
  - 私は何級くらい？ → 申立書を、自分で書きたい
  - 申立書を、自分で書きたい → どこに出せばいい？(提出へ)
  - いくらもらえる？ → 申請の流れ(`/shinsei`)
  それ以外の相互リンクは消す(5つが「仲間」に見える導線を残さない)。

### 4-3 「自分の場合を確かめる」という語
5機能の総称としては**使わない**。この語が残るのは、誤解カード48枚の中の節名「自分の場合を確かめる」だけ(あれは元の用法)。
`data/dougu.ts` の `TOOLS` は残してよい(記事・ステップへの埋め込みの元データ)。`JIBUN_ORDER` / `JibunCards` は、トップと `/dougu` から外れるので `/hajimete` の2枚以外で使われなくなる。使われない部品は消す。

## §8 コミットと検証
順番どおり1コミットずつ。
1. `feat(site): トップの「申請の流れ」に、各ステップで使う機能を埋め込む`(§1-2 と §3)
2. `feat(site): トップを申請したい人の順に並べ直し、確かめるの帯と選ぶの独立セクションを畳む`(§1 の残り)
3. `feat(site): ナビを入口の軸と読み物に絞り、状況からを足す`(§2)
4. `refactor(site): 5機能の一覧を廃止し、各機能を申請の流れとお金の話の下に置く`(§4, §5)

各コミットで: `rm -rf .next && npm run build && npm run prelaunch:check`。ページ数は4コミット目で 167→166(`/dougu` の一覧が消える)。A 全項目・C-1 ○・C-5 で `/dougu`→`/shinsei` が301、B-1/B-2 悪化なし。a4-insatsu のカードがバイト一致。`content/columns` と `data/hubs` に差分0。
最後に 375px / 1280px のトップと /shinsei のスクリーンショットを `docs/verification/structure-2026-09-03/` に保存し、main へ push。

デプロイ後、本番で確認して報告:

- ナビが7項目で「状況から」があり「自分の場合」が無い。375px で崩れていない

- フッターが3列で、5機能が並んでいない
- a4-insatsu のカードがバイト一致
