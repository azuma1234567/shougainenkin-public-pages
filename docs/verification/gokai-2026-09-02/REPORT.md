## 6. 配分表が触れていない公開ハブ（0枚のまま）

`/byoki/tougou`・`/byoki/tenkan`・`/byoki/shinzou`・`/byoki/shitai`・`/nayami/fushikyu`・`/nayami/shikyuu-teishi` の6本には、配分表がカードを割り当てていない。

配分表は「全13ハブ」と書かれた時点のもので、その後に公開されたハブ（統合失調症・てんかん・心臓病・肢体）と、もともと表に載っていないハブ（不支給・支給停止）が対象外になっている。
**原稿にない紐づけを足すと完了条件2の「配分表と一致」を壊すため、勝手な割り当てはしていない。** 第5弾以降で補うか、既存カードの `対応ハブ` を追記するかは指示を待つ。`npm run verify:gokai` は0枚のハブを毎回一覧で出力する。

## 8. OG画像の日本語フォントを同梱した（実バグの修正）

最初の本番ビルドで、`/gokai/munenkin-owari` のOG画像が**漢字すべて豆腐（□）**、`/gokai/kounin-daikou` が「本当は」の本文が枠外に**横あふれ**していた。

原因: `next/og`（Satori）は同梱フォント（Noto Sans ラテン）にない文字を、画像ごとにビルド時 Google Fonts へ取りに行く。この取得が `ECONNRESET` で失敗すると、その画像だけ文字が欠けたまま生成される（ビルドログに `Failed to load dynamic font for …` と出るが、ビルド自体は成功扱い）。また取得待ちで60秒を超えた画像がリトライされ、ビルドが不安定・低速になっていた。

対応:
- Noto Sans JP（OFL、`lib/fonts/OFL.txt` 同梱）の可変フォントから、サイトの原稿に出てくる文字＋かな・記号・丸数字の範囲だけを Regular(400)/Bold(700) の静的TTFに切り出し、`lib/fonts/` に置いた（各 約760KB、2,145符号位置）。生成は `scripts/build-og-font.py`（fontTools）。
- `lib/gokai-og.tsx` はこのフォントを `readFile` で読み、`ImageResponse` の `fonts` に渡す。`next.config.ts` の `outputFileTracingIncludes` で関数バンドルにも含める。
- `lib/fonts/coverage.json`（収録符号位置の一覧）を出力し、`verify:gokai` が **OG画像に載せる全文字（誤解の一文・本当は・ラベル・サイト名）が収録済み** であることを毎回検査する。新しい漢字を含むカードを足したら検証が落ちるので、`build-og-font.py` を再実行する。
- 横あふれは、Satoriの行内テキストに `flex: 1; minWidth: 0` がなく縮まなかったのが原因。指定を足し、検証にも左右の余白帯（x=20 / x=1180）の検査を追加した。

結果（クリーンビルド後の `.next/server/app/gokai/*/opengraph-image.body` 48枚を直接検査）: 1200×630、上下左右の余白帯に文字なし **48/48**。ビルドログの `Failed to load dynamic font` は3件あるが、いずれもコラム記事のOG画像（`lib/column-og.tsx` はまだネットワーク取得のまま）で、誤解カードは0件。
